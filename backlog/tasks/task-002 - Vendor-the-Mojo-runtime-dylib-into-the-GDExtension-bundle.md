## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The Mojo ABI uses `List`/`Error`, so `core/build-output/lib/libdopewars.a` references the Mojo runtime (`KGEN_CompilerRT_*`). TASK-001.05 made `extension/SConstruct` link `libKGENCompilerRTShared.dylib` from `core/.venv/lib/python3.13/site-packages/modular/lib/` by absolute path and bake that path into the GDExtension's rpath.

That is a dev-build dependency: the built `game/bin/libdopewars.*` only loads while `core/.venv` exists at that exact path, and it is not distributable. This task vendors the runtime so the bundle is self-contained.

**Scope:**
- Copy `libKGENCompilerRTShared.dylib` next to the framework (or into it) as part of `task extension:build`, and set the rpath to `@loader_path` (or `@loader_path/..`) instead of the venv path.
- Handle the Linux equivalent: copy the `.so` and use `$ORIGIN` in the rpath.
- Gitignore the copied runtime (it is a build artifact, not source).
- Keep `task check` green.

**Out of scope:** release/export packaging, code signing, notarization, Windows/web.

References: `extension/SConstruct`, `AGENTS.md` (the "Mojo runtime" note), `~/git/jumpnbump/extension/SConstruct` for how that repo handles its own runtime dependency.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
### What landed

- `extension/SConstruct` — the runtime is located in the venv by full path, the build
  links it there as before, and a SCons command copies the runtime plus its transitive
  @rpath/NEEDED closure into the extension's own output location (framework directory on
  macOS, game/bin/ on Linux). The rpath is now self-relative (`@loader_path` /
  `$ORIGIN`) instead of the venv directory, so no core/.venv path reaches a load command.
- `.gitignore` — the vendored runtime files (named, at any depth) are ignored; they are
  build artifacts regenerated by `task extension:build`.
- `AGENTS.md` — the "Mojo runtime" note now describes the vendoring; only
  `task core:abi:shared-lib` (conformance tooling) still links against the venv path.

### Why the whole closure, not just the runtime

`libKGENCompilerRTShared` itself references `libMSupportGlobals` and
`libAsyncRTRuntimeGlobals` by @rpath install name; vendoring only the runtime would
swap one unresolvable reference for another. The SConstruct walks `otool -L` / `readelf -d`
from the runtime and copies every dependency it finds in the venv's lib directory, so the
set follows a Mojo upgrade rather than a hard-coded list.
